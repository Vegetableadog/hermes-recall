## 决定

### 1. 数据字段 Contract ✓ 已确认：Echo 2026-08-12

- **memory 对象**（可选子对象，V1.0 核心字段保持稳定）：
  - `memory_type`：单值枚举 `task / idea / fact / preference / experience / unknown`
  - `importance`：`low / normal / high`，默认 `normal`
  - `entities`：非空字符串数组，去重、保持用户可读文本
  - `related_ids`：有效 Record ID 去重数组（轻量关联，无类型/方向/置信度）
- **timeline**：事件数组 `{date, event, result?}`，时间强制 ISO 8601 带时区
- **parent_id**：可选，指向父回响（不覆盖，建立关联）
- **状态模型**：现有中文枚举（待处理/进行中/已完成/已归档）**新增"等待反馈"**，形成五状态：待处理 → 进行中 → 等待反馈 → 已完成 → 已归档
- **状态机设计**（用户确认，2026-08-12）：
  - `status` 只存当前快照（现在到哪了）；`timeline` 存完整轨迹（之前发生了什么）——两者各司其职
  - 流转允许回头：待处理↔进行中、进行中→等待反馈、等待反馈→待处理/进行中、已完成→进行中（现有 5.10 已允许）
  - 每次状态流转自动追加 timeline 事件，无需用户手动记录
  - 同一事情无论反复多少次，在同一条 Record 内累积 timeline，不新建记录
- 理由：memory 对象收敛稳定 V1.0 核心字段；"等待反馈"来自真实使用场景（用户反馈"等外部反馈→保持+等待反馈"）；timeline/parent_id 是 FR-003 引擎输入契约，V1.1 起数据按契约积累

**冻结补充（2026-08-12，Echo 确认）**：

- **Reminder 状态机**：FR-002 五状态 + failed/cancelled 终态 = 七状态 `pending / reminded / waiting_response / completed / archived / failed / cancelled`；07 §10.1 六状态（scheduled/triggered/partially_completed）+ Delivery/Attempt 实体明确标为 V1.5 Target，V1.1 不引入 Delivery/Attempt 实体，分层并存
- **reminder_status 迁移映射**：pending→pending；sent→reminded；failed→failed（标注 V1.5 由 Delivery 聚合判定替代，不回头修数据）；cancelled→cancelled
- **timeline.result 语义**：附加说明/上下文（可承载结果、等待对象、备注、预期下一步），不强制"已完成事实"
- **memory.waiting_for**（可选 string）：与 status 联动——进入等待反馈时写入；退出时先由自动 timeline 事件固化、再清空；Validator 双向约束：waiting_for 非空 ⇒ status=等待反馈；status=等待反馈时 waiting_for 可空
- ✓ 已确认：Echo 2026-08-12
- 影响：Schema v2 升级、迁移补默认值、validator 覆盖

### 2. AI 确认策略 ✓ 已确认：Echo 2026-08-12

- 采纳"建议-不伪装"：Hermes 可建议 memory 字段；高置信度直接建议，低置信度用默认/空值并向用户说明
- 不把低置信度推断伪装成事实；不做强制确认流程（轻便第一），靠"不伪装"原则兜底

### 3. 关联删除策略 ✓ 已确认：Echo 2026-08-12

- 采纳"保留 + 报告"：`related_ids` 指向的记录被删除时，关联 ID 保留，validator 与展示层报告悬空；不自动级联删除
- 删除时展示受影响的关联，由用户显式处理

### 4. Gateway 缺陷归属 ✓ 已确认：Echo 2026-08-12
