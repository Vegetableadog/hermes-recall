# ADR-001：当前阶段继续使用 JSON 作为主存储

- 状态：Accepted
- 决策日期：2026-08-10
- 适用产品基线：v1.0
- 当前数据 Schema：1.01
- Supersedes：无
- Superseded by：无

## 1. 背景

Hermes Recall 当前是面向个人用户的本地智能备忘录与长期记忆基础。系统需要保存：

- Recall Records；
- Reminder 相关字段；
- History Events；
- 本地配置；
- 由主数据生成的 Markdown View。

当前实现使用：

- `recall.json` 保存主数据；
- `recall_history.json` 保存审计历史；
- `config.json` 保存当前 webhook 备用配置；
- Markdown 保存派生阅读视图。

未来路线包含结构化记忆、关联记录、Notification Delivery、SQLite 和 Vector Memory，因此需要明确：当前是否应立即迁移数据库，还是继续使用 JSON。

## 2. 决策

Hermes Recall 在当前产品阶段继续使用 JSON 作为主存储。

具体约定：

1. `recall.json` 继续作为当前 Recall Records 的唯一事实来源；
2. `recall_history.json` 继续作为审计历史，不作为当前状态事实来源；
3. Markdown View 继续由 JSON 单向生成；
4. 当前不因路线图中存在 SQLite 就立即迁移；
5. JSON 方案不是永久承诺；
6. 当复审触发条件成立时，重新评估 SQLite；
7. Vector Index 即使未来引入，也只能是可重建的派生索引，不能取代结构化主数据。

## 3. 决策理由

### 3.1 当前数据规模和使用方式适合 JSON

当前产品是个人、低并发、本地运行。主要操作是：

- 新增少量 Records；
- 查询和搜索；
- 更新状态；
- 周期扫描 Reminder；
- 生成 View；
- 备份和迁移。

现阶段尚无真实证据表明数据库是解决用户问题的首要条件。

### 3.2 JSON 易于检查和恢复

JSON 具有：

- 人类可读；
- 无额外服务；
- 易复制备份；
- 易于在隔离目录验证；
- 便于早期调整 Schema；
- 与当前纯标准库 CLI 匹配。

### 3.3 立即迁移会增加不必要风险

数据库迁移会新增：

- Migration 和 rollback；
- Schema 管理；
- 事务边界；
- 查询适配；
- 备份恢复方式变化；
- JSON 与数据库双写风险；
- 用户安装和排障成本。

在自动化测试和 Migration 基线尚未完整建立前立即迁移，风险高于当前收益。

### 3.4 当前更重要的问题不在存储引擎

现阶段优先级更高的是：

- 完整测试基线；
- 数据备份和恢复；
- v1.1 数据 Contract；
- Reminder 投递状态可靠性；
- Validator 覆盖；
- Simple Mode 和配置体验。

SQLite 不能自动解决这些问题。

## 4. 考虑过的替代方案

### 4.1 立即迁移 SQLite

优点：

- 支持事务；
- 支持索引和组合查询；
- 多实体关系更自然；
- 避免每次整体覆盖主文件；
- 为 Reminder、Delivery 和关系模型提供表结构。

未采用原因：

- 当前缺少真实性能或并发压力；
- Migration 和 rollback 尚未建立完整自动化测试；
- 会提前增加产品和运维复杂度；
- v1.1 和 Notification 最终实体模型尚未冻结；
- 可能在数据 Contract 未稳定时重复迁移。

### 4.2 JSON 与 SQLite 长期双写

优点：

- 可以逐步验证数据库；
- 短期保留 JSON 兼容。

未采用原因：

- 容易产生两个事实来源；
- 失败顺序造成数据不一致；
- 需要复杂的对账和修复；
- 长期双写会增加维护成本。

如果未来迁移需要短期双写，必须明确唯一写入入口、事实来源、对账机制和退出计划。

### 4.3 立即采用 Vector Database

优点：

- 支持语义检索；
- 为长期 Recall 提供相似度搜索。

未采用原因：

- Vector Search 不适合作为主数据事实来源；
- 当前还没有稳定评测集证明关键词和结构化查询不足；
- 增加 Embedding、隐私、成本和索引一致性问题；
- 结构化记忆模型尚未完成。

### 4.4 以 Markdown 作为主存储

优点：

- 人类可读；
- 编辑方便。

未采用原因：

- 字段和状态约束弱；
- 容易与 JSON 形成双事实来源；
- Reminder 和 Migration 难以可靠管理；
- 手工编辑难以保持 History 和 Schema 一致。

## 5. 正面后果

- 保持当前实现和用户数据兼容；
- 避免没有真实需求支撑的提前迁移；
- 继续使用纯标准库和轻量安装；
- 备份、审查和恢复路径简单；
- 可以先冻结 v1.1 和 Notification 数据 Contract；
- 项目可以将资源集中在测试、数据安全和 Reminder 可靠性；
- 为未来数据库迁移保留明确复审入口。

## 6. 负面后果与风险

### 6.1 整体覆盖写入

当前保存会整体覆盖 `recall.json`，存在进程中断、磁盘错误或部分写入风险。

应对：

- 增加原子临时文件替换；
- 写入前后验证；
- 定期备份；
- 故障注入测试。

### 6.2 缺少事务

主数据和 History 分别写入，无法保证跨文件事务一致性。

应对：

- 明确错误并避免伪报成功；
- 增加一致性检查；
- 将该问题作为 SQLite 复审信号之一。

### 6.3 查询性能随数据量增长

当前查询需要读取和扫描 JSON，数据增长后可能变慢。

应对：

- 测量文件大小、读取耗时、写入耗时和查询耗时；
- 不凭纸面记录数量直接迁移；
- 使用真实基准决定阈值。

### 6.4 多实体表达困难

独立 Reminder、Delivery Attempt 和关系网络在单一 Records 数组中不易表达。

应对：

- 先冻结 Target Contract；
- 评估 JSON 多集合与 SQLite 表结构；
- 不把平台细节持续塞入 Record。

### 6.5 并发写入风险

多个进程同时写入可能导致最后写入覆盖前一写入。

应对：

- 当前维持单用户、低并发假设；
- 增加锁或原子声明前先写并发测试；
- 出现多实例需求时触发复审。

## 7. 实施约束

继续使用 JSON 不代表维持现状不改。当前阶段必须：

1. 保持 `recall.json` 为唯一事实来源；
2. 禁止 Markdown 双向维护；
3. 所有业务写入通过 Core/CLI；
4. 为 Schema 变化提供 Migration；
5. Migration 前备份；
6. 逐步增强 Validator；
7. 建立自动化回归测试；
8. 测量真实性能和失败数据；
9. 不在公开仓库提交用户数据；
10. 避免长期双写。

## 8. 复审触发条件

出现以下一项或多项时，必须重新评估存储方案：

### 8.1 性能

- 主文件读取、查询或保存延迟影响日常使用；
- 文件大小导致备份、View 或 Scheduler 明显变慢；
- 实测达到团队确认的性能阈值。

### 8.2 可靠性

- 整体覆盖造成数据损坏或不可接受的风险；
- 需要原子多实体更新；
- 主数据与 History 不一致频繁发生；
- 需要可靠事务和约束。

### 8.3 数据模型

- Reminder、Delivery、Attempt 成为独立实体；
- Record Relations 需要大量引用和组合查询；
- 多渠道 Notification 需要独立状态持久化；
- History Event 需要稳定查询和保留策略。

### 8.4 使用模式

- 出现多进程或多实例并发写入；
- 出现正式多用户隔离需求；
- 需要跨设备同步；
- 需要高频写入或复杂过滤。

### 8.5 语义检索

- 真实评测证明关键词和结构化查询不足；
- Vector Index 需要与稳定结构化主存储关联；
- Embedding 隐私和重建策略已明确。

原始路线中按 Record 数量划分 JSON 和 SQLite 阶段，可以作为观察参考，但不是自动触发迁移的硬阈值。

## 9. 复审时必须回答

1. 当前真实瓶颈是什么；
2. SQLite 是否能直接解决该瓶颈；
3. 是否有基准测试和失败证据；
4. Target 数据模型是否已经冻结；
5. 如何 Migration 和 rollback；
6. 如何验证 Record、Reminder、History 和关系数量；
7. 是否需要短期双写，何时结束；
8. Markdown View 如何保持；
9. 用户如何导出和恢复；
10. Vector Index 是否保持可重建派生数据；
11. 产品、Skill 和 Schema 版本如何变化；
12. 是否经过用户验收。

## 10. 决策影响

### 10.1 对 v1.1

v1.1 结构化记忆默认继续以 JSON 为基础，但最终 Contract 必须避免阻塞未来 SQLite 映射。

### 10.2 对 v1.4/v1.5

Reminder、Delivery 和 Attempt 的 Target Contract 可以先设计，但是否在 JSON 中使用独立集合，需在实施前再次评估。如果可靠投递要求原子多实体更新，可能触发本 ADR 复审。

### 10.3 对测试

`../正式基线/05-测试计划.md` 需要覆盖：

- 原子写入候选方案；
- 主数据与 History 不一致；
- 并发写入；
- 大文件基准；
- Migration 和 rollback；
- Vector Index 可重建。

### 10.4 对运维

`../正式基线/08-部署与运维.md` 继续以文件备份、校验和和隔离恢复为主。引入数据库后必须创建新的备份和恢复 ADR 或更新决策链。

## 12. 验收结论

当前阶段继续使用 JSON 的收益高于立即迁移数据库的收益。

该决策成立的前提是：项目持续加强备份、Validator、自动化测试、原子写入和真实性能测量。一旦事务、多实体、并发或真实性能需求达到复审条件，应创建新的 ADR 重新选择存储方案，而不是无限延长 JSON 的适用范围。
