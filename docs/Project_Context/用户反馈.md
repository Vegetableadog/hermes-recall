# 使用反馈与观察

本文件仅整理历史资料中已经出现的事实、现象和复盘问题；不提出新方案。

## 已记录的现象

- v1.0 后的既定策略是先真实使用、收集反馈，再决定下一阶段，而不是继续预先开发。
- 当前 Reminder 在输出后可能被置为 `sent`，但 Gateway/平台投递可能随后失败；因此“脚本或 cron 成功”不等于“用户收到”。
- Reminder 的发送状态与 Record 是否完成是不同问题。提醒后，任务/事项的状态仍需独立表达。
- 当前记录模型以单条 Record 的当前状态为中心；事情在推进、变化或结束时，尚无已实现的结构化演化、父子 Recall 或关联时间线能力。
- 当前搜索主要是关键词与标签匹配，不能表达更长期的语义关联或上下文召回。
- 普通用户不应被迫理解 Provider、Scheduler、Identity Mapping、Schema Version 和 Migration 等内部概念。

## 与 Memory Evolution 的关系

历史路线将 `memory_type`、`importance`、`entities`、`related_ids`、关联与回顾列为未来方向，原因是现有记录与提醒闭环尚不能完整呈现信息之间的连接，或事情随时间发展的变化。它们仍是规划，未被当作当前能力。

## 后续复盘关注点（既有问题）

- 用户是否愿意持续输入信息？
- 哪些信息值得长期保存？
- 哪些提醒真正有价值，哪些造成打扰？
- 用户希望 Hermes 主动说什么？
- Recall 在真实使用中更像工具、助手还是长期伙伴？
