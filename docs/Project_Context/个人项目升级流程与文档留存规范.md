# 个人项目升级流程与文档留存规范

> 状态：Proposed  
> 适用对象：Hermes Recall 及同类个人长期项目  
> 目标：让项目可追溯、可继续，而不是模拟企业流程。

## 1. 为什么需要这份规范

个人项目的目标不是最大化流程覆盖率，而是在不制造负担的前提下，保留足够清晰的判断、计划和结果。

当前混乱的根源不是资料太多，而是不同 Agent 的建议、综合结论、当前事实和未来计划混在同一层级；同一问题可以同时出现多份“看似当前”的文档。因此，今后要把“输入”和“决定”分开，并始终让每个升级只有一个综合后的执行口径。

## 2. 核心约定

1. **一项升级，一个主档案。** 每个版本升级只能有一个 `升级总览.md` 作为范围、状态和链接入口。
2. **建议不是决定。** Agent、灵感、调研和讨论产物先作为 Input 保留；只有综合后写入的结论才能指导实现。
3. **一个主题，一个当前口径。** 同一主题的 Current 说明只保留一个主文档；其他材料通过链接引用，不能复制后各自继续演化。
4. **历史不删除。** 已有资料不被覆盖；过时或未采用的材料标为 Historical / Input / Superseded。
5. **升级前先冻结最小范围。** 开发前只确认本次要解决的问题、明确不做的内容、关键数据/兼容决策和验收方式。
6. **证据跟着升级走。** 测试结果、迁移记录和用户验收写在该升级档案中，不另建散落的“最终版”文档。
7. **轻量优先。** 没有明确用途的会议纪要、日报、重复计划、状态周报、矩阵和审批表都不创建。

## 3. 未来目录方案

以下是新资料的目标结构。现有 `docs` 文件不在本次规范落地时移动；迁移或清理必须单独确认。根目录的 1–8 是既有正式基线，仍保留其连续编号与互相引用。

```text
docs/
├── 00_项目导航.md                 # 唯一入口：当前版本、当前升级、权威文档链接
├── 01-项目总览.md                  # 既有项目级基线；后续受控校准
├── 02-系统架构.md                  # 既有核心基线：架构
├── 03-数据模型.md                  # 既有核心基线：数据契约
├── 04-开发路线图.md                # 既有核心基线：长期路线
├── 05-测试计划.md                  # 既有核心基线：质量与验收
├── 06-产品需求.md                  # 既有核心基线：产品需求
├── 07-提醒与通知.md                # 既有核心基线：提醒专项
├── 08-部署与运维.md                # 既有核心基线：运行与维护
├── Project_Context/                # 长期背景、原则、当前状态、决策摘要
├── Upgrades/
│   └── V1.1/
│       ├── 升级总览.md             # 本次唯一执行口径
│       ├── 输入材料/               # 不同 Agent 的原始建议，只读保留
│       ├── 综合与决策.md           # 取舍、待确认项、范围冻结记录
│       ├── 实施与验收.md           # 分步实施、测试证据、用户验收、发布结论
│       └── 归档说明.md             # 完成后说明最终结果、未完成项和后续入口
```

### 3.1 根目录 1–8 的定位

这八份文件不是单次升级的材料，也不是 Agent Input；它们构成项目的既有**正式基线**。不同文档各自负责不同的问题，升级档案只能引用它们，不能复制后各自继续维护。

| 文件 | 基线职责 | 对 V1.1 的关系 |
|---|---|---|
| `01-项目总览.md` | 项目定位、当前状态、版本口径和文档边界。 | 当前目录状态表仍将 02–08 写为 Planned，与实际文件冲突；应保留并列为后续校准项，不再单独承担导航。 |
| `02-系统架构.md` | 架构边界、数据流与目标分层。 | 提供 Intent Layer 等架构依据。 |
| `03-数据模型.md` | Schema、字段、兼容与迁移原则。 | 约束结构化记忆的 Contract。 |
| `04-开发路线图.md` | 版本顺序、依赖、进入和完成条件。 | 是 V1.1 候选范围与门禁的主要来源。 |
| `05-测试计划.md` | 测试层级、回归和验收。 | 提供 V11-NLU、Migration 等测试门禁。 |
| `06-产品需求.md` | 用户、场景、体验与范围。 | 提供回响式交互需求与非目标。 |
| `07-提醒与通知.md` | Reminder / Notification 专项 Contract。 | 主要面向 V1.4/V1.5；V1.1 仅引用现有边界，不提前实现其 Target。 |
| `08-部署与运维.md` | 数据、备份、恢复、发布与运行维护。 | 约束升级前备份、迁移、回滚和验收。 |

`00_项目导航.md` 是新的轻量入口，不复制 1–8 的详细内容。它只回答：当前版本是什么、当前正在进行哪个升级、每个主题去哪里找唯一权威文档、哪些文件处于 Input / Frozen / Evidence / Historical 状态。

### 3.2 文件职责与创建门槛

| 位置 | 何时创建 | 只放什么 | 不放什么 |
|---|---|---|---|
| `00_项目导航.md` | 建立新体系时创建并少量维护 | 当前版本、当前升级、唯一权威链接、资料状态说明 | 详细方案、测试记录、Agent 原文。 |
| `Project_Context/` | 长期事实或原则变化时 | 跨版本稳定背景、原则、当前状态摘要 | 某一次升级的实施细节。 |
| `Upgrades/Vx.y/输入材料/` | 收到一份有保留价值的外部/Agent 建议时 | 原始建议、来源、日期、问题范围 | 修改后的综合结论。 |
| `升级总览.md` | 升级启动时 | 目标、状态、范围、非目标、唯一链接入口 | 多份并行方案。 |
| `综合与决策.md` | 输入收集后 | 比较后的采纳/暂缓/否决、待确认项、冻结结论 | 未经标记的原始观点。 |
| `实施与验收.md` | 范围冻结后 | 最小实施切片、测试、迁移、验收结果 | 长期背景的重复解释。 |
| `归档说明.md` | 升级结束时 | 完成事实、已知遗留、下次升级入口 | 新需求设计。 |
| `adr/` | 决定会影响长期数据、架构、运维或迁移成本时 | 背景、取舍、决定、复审条件 | 普通功能进度和局部缺陷。 |

## 4. 文档状态与命名

每个新文档顶部必须注明一个状态：

- **Current**：已实现且已核验的当前事实。
- **Proposed**：等待综合、确认或范围冻结的方案。
- **Frozen**：本次升级已确认的范围与 Contract；变更必须留痕。
- **Evidence**：测试、迁移或验收事实。
- **Historical / Input**：保留来源，不作为当前执行规范。
- **Superseded**：被新版结论替代，保留链接指向替代文档。

文件名使用中文职责名，避免 `final`、`最新`、`新版`、`修改版`、`Agent建议` 等会随时间失效的名称。输入材料使用：

```text
YYYY-MM-DD_来源_主题.md
例如：2026-08-11_Agent-A_V1.1数据模型建议.md
```

每份 Input 首行标注：来源、日期、回答的问题、是否已被综合；它永远不直接改变 Current 或 Frozen 文档。

## 5. 轻量个人升级流程

### 步骤 0：提出升级卡

在 `升级总览.md` 写四行即可：

- 想解决的真实问题；
- 本次目标版本；
- 已知约束（数据、提醒、兼容、隐私）；
- 暂不做什么。

没有真实问题或用户反馈时，升级保持 Idea，不进入开发。

### 步骤 1：收集输入

不同 Agent 可以独立提出建议，但每份建议都进入 `输入材料/`，不覆盖主文档。提问时必须说明：问题边界、现有事实来源、希望得到的内容，以及“建议不等于决定”。

### 步骤 2：一次综合

由一个维护者创建或更新 `综合与决策.md`。针对每个关键问题只记录：

- 已采纳：理由与影响；
- 暂缓：缺少什么证据；
- 不采用：简短理由；
- 待用户确认：明确的问题和可选项。

综合完成后，`升级总览.md` 只链接该文件，不再罗列多份 Agent 结论。

### 步骤 3：范围冻结

冻结前确认以下最小内容：

- 本次功能和非目标；
- 数据 Contract 与旧数据处理方式；
- 需要用户确认的危险操作；
- 回归范围和完成判据；
- 是否需要 ADR。

冻结后将 `升级总览.md` 与 `综合与决策.md` 标为 Frozen。新增想法进入下一版本或 Input，不在实现中途静默加塞。

### 步骤 4：小切片实现

每次只完成一个可验证切片，例如“字段读写与校验”或“删除确认”。实施记录只写：目标、改动范围、测试结果、未解决问题。无需日报。

### 步骤 5：验收与收尾

在 `实施与验收.md` 记录：通过的测试、迁移/回滚证据、已知遗留和用户验收。然后创建 `归档说明.md`，把 `升级总览.md` 状态改为 Completed，并在 `00_项目导航.md` 更新当前版本入口。

## 6. Agent 协作规则

1. 同一轮可以收集多份建议，但只指定一位“综合者”更新 `综合与决策.md`。
2. Agent 开始建议前先读取 `00_项目导航.md`、当前升级的 `升级总览.md` 和已冻结的决定。
3. Agent 输出必须标注它是事实核对、方案建议、风险清单还是实施结果。
4. Agent 不得将自己的建议写成 Current/Frozen，除非维护者明确授权并完成综合。
5. 发现重复文档时，不新建第三份总结；在综合文档中标注主来源和替代关系。
6. 任何冲突先回到实际数据、当前源码和 Current 文档核实，再讨论方案。

## 7. V1.1 的建议落地方式

V1.1 现有的需求与方案文档仍属于 Proposed Input，不应直接作为唯一执行口径。建议下一步：

1. 创建 `Upgrades/V1.1/` 的空档案结构；
2. 将现有各 Agent 的 V1.1 建议**复制**或链接登记为 Input，保留原文件；
3. 仅建立一份 `综合与决策.md`，先解决数据字段 Contract、AI 确认策略、关联删除策略、Gateway 缺陷归属和展示范围；
4. 决策确认后，再生成 Frozen 的 `升级总览.md` 与 `实施与验收.md`。

本次不应直接移动、删除、重命名既有文档，也不应在未综合前开始 V1.1 实现。

```md
本次目标：

实施与验收：链接到《实施与验收》
```

```md

输入清单：
```
