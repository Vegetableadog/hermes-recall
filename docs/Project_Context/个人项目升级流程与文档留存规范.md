## 1. 这份规范存在的理由

个人项目的目标不是最大化流程覆盖率，而是在不制造负担的前提下，保留足够清晰的判断、计划和结果。

**混乱的根源**：不同 Agent 的建议、综合结论、当前事实和未来计划混在同一层级；同一问题出现多份"看似当前"的文档。因此把"输入"和"决定"分开，每个升级只有一个综合后的执行口径。

**单人开发者原则**：自己不会骗自己，所以不需要审批链、多角色制衡这类防内鬼设计。流程只防两件事——跨会话失忆和数据丢失。流程的唯一目标：未来的我或未来的 Agent 打开文档 5 分钟内能知道——现在在做什么、做到哪了、下一步干什么。超出这个目标的流程都是负债。

**七成把握原则**：不追求一步到位。核心资产（数据、决策记录）七成情况下不丢、不混乱即可；出问题能快速发现、能低成本修。规范本身也被允许修订，修订规则见第 8 节。

## 2. 核心约定

1. **一项升级，一个主档案。** 每个版本升级只能有一个 `升级总览.md` 作为范围、状态和链接入口。
2. **建议不是决定。** Agent、灵感、调研和讨论产物先作为 Input 保留；只有综合后写入的结论才能指导实现。
3. **一个主题，一个当前口径。** 同一主题的 Current 说明只保留一个主文档；其他材料通过链接引用，不能复制后各自继续演化。
4. **历史不删除。** 已有资料不被覆盖；过时或未采用的材料标为 Historical / Input / Superseded。版本历史由 git 承担。
5. **升级前先冻结最小范围。** 开发前只确认本次要解决的问题、明确不做的内容、关键数据/兼容决策和验收方式。
6. **证据跟着升级走。** 测试结果、迁移记录和用户验收写在该升级档案中，不另建散落的"最终版"文档。
7. **轻量优先。** 没有明确用途的会议纪要、日报、重复计划、状态周报、矩阵和审批表都不创建。
8. **版本归 git，状态归文档，文件名只承担职责。** 文件名用中文职责名，不出现 final、最新、新版、修改版或版本号；版本号写在文档内容里。

## 3. 升级分级：一刀切

判断标准只有一条：**这次升级是否改变数据的读写结构、存储方式或兼容性（含迁移）？**

- **不动数据**：走最轻流程——升级卡四行（第 6 节步骤 0）+ 切片记录（步骤 5）。不建完整档案。
- **动数据**：走完整流程（第 6 节五件套）。
- **拿不准时按"动数据"对待**：宁可多记一行，不可丢数据。

纯 UI、文案、展示层改动按"不动数据"处理。

```text

├── 正式基线/                       # 01–08 正式基线（互相引用，升级档案只引用不复制）
│   ├── 01-项目总览.md
│   ├── 02-系统架构.md
│   ├── 03-数据模型.md
│   ├── 04-开发路线图.md
│   ├── 05-测试计划.md
│   ├── 06-产品需求.md
│   ├── 07-提醒与通知.md
│   └── 08-部署与运维.md
├── Project_Context/                # 长期背景、原则、当前状态、决策摘要（本规范所在处）
├── Upgrades/
│   └── V1.1/
│       ├── 升级总览.md             # 本次唯一执行口径
│       ├── 输入材料/               # 原始建议链接登记，只读保留
│       ├── 综合与决策.md           # 取舍、待确认项、范围冻结记录
│       ├── 实施与验收.md           # 分步实施、测试证据、用户验收、发布结论
│       └── 归档说明.md             # 完成后说明最终结果、未完成项和后续入口
├── archive/                        # Historical 原稿与 Completed 升级；保持原样
└── adr/                            # 仅记录有长期代价的重大决策
```

**归档线**：升级 Completed 后，将该升级整目录移入 `archive/upgrades/Vx.y/`，`Upgrades/` 只保留进行中的升级；导航中留一条历史链接。既有文件本次不移动；迁移或清理必须单独确认。

**链接规则**：升级档案（Upgrades/ 及其归档副本）内的跨目录链接统一写**仓库根绝对路径**（以 `/` 开头，如 `/docs/Project_Context/xxx.md`，GitHub 与 VS Code 仓库打开均可点击），目录随归档移动后链接依然有效。

## 5. 文档状态与命名

每个新文档顶部必须注明一个状态：

- **Current**：已实现且已核验的当前事实。
- **Proposed**：等待综合、确认或范围冻结的方案。
- **Frozen**：本次升级已确认的范围与 Contract；变更必须留痕。
- **Evidence**：测试、迁移或验收事实。
- **Historical / Input**：保留来源，不作为当前执行规范。
- **Superseded**：被新版结论替代，保留链接指向替代文档。
- **Completed**：升级总览专用终态，表示该升级已完成并归档。

**状态流转权在用户（维护者）**：Proposed→Frozen→Completed 的流转必须经用户确认；Agent 只能提议流转、记录证据，不得自行改状态。

**确认留痕**：用户对"待用户确认"项作出决定时，在 `综合与决策.md` 对应决定行尾标注「✓ 已确认：Echo 2026-08-12」，保证决定可追溯。

命名：文件名使用中文职责名。输入材料使用 `YYYY-MM-DD_来源_主题.md`，首行标注来源、日期、回答的问题、是否已被综合；它永远不直接改变 Current 或 Frozen 文档。

## 6. 轻量个人升级流程

### 步骤 0：提出升级卡
在 `升级总览.md` 写四行：想解决的真实问题；本次目标版本；已知约束（数据、提醒、兼容、隐私）；暂不做什么。四行即模板骨架，范围冻结（步骤 3）时补齐为完整模板。同时更新 `00_项目导航.md` 登记当前升级并链接升级总览（若导航已超前登记，同步修正为指向升级总览）。没有真实问题或用户反馈时，升级保持 Idea，不进入开发。

### 步骤 1：收集输入
不同 Agent 可以独立提出建议，但每份建议**登记为链接**进入 `输入材料/`，不复制、不覆盖主文档。提问时必须说明：问题边界、现有事实来源、希望得到的内容，以及"建议不等于决定"。登记后做**输入充分性检查**：本次升级的每个决策问题（见步骤 2）在输入材料中是否都有依据；缺的补收集后再综合。

### 步骤 2：一次综合
由一个维护者创建或更新 `综合与决策.md`。针对每个关键问题只记录：已采纳（理由与影响）、暂缓（缺少什么证据）、不采用（简短理由）、待用户确认（明确的问题和可选项）。综合完成后，`升级总览.md` 只链接该文件，不再罗列多份 Agent 结论。

### 步骤 3：范围冻结
冻结前确认最小内容：本次功能和非目标；数据 Contract 的方向与约束（不写完整契约，细节留给实现）；**受影响基线清单**（即校准授权范围）；需要用户确认的危险操作；回归范围和完成判据；是否需要 ADR。冻结后将 `升级总览.md` 与 `综合与决策.md` 标为 Frozen。新增想法进入下一版本或 Input，不在实现中途静默加塞。

**基线校准规则**：冻结时只确认 Contract 的方向与约束，不校准基线内容。实现期间基线允许滞后，事实以代码与切片记录为准（源码第一权威，见第 7 节规则 6）。收尾时（步骤 6）由 Agent 从代码反推一次性校准受影响基线（独立 commit），Echo 抽查确认。实现失败时基线未动、零回滚成本；失败原因记入 `实施与验收.md`，缩减范围重新冻结。

### 步骤 4：模拟推演（dry run）

范围冻结后、实现开始前，按文档流程把本次升级从头到尾**纸面走一遍**，不落实现代码。检查：

- 文件流转是否闭环（每个动作从哪个文件到哪个文件）；
- 相对链接在归档后是否仍有效（重点：Upgrades/ 整目录移入 archive/ 后深度变化）；
- 状态流转是否明确（谁、在什么时候、把哪个状态改成什么）；
- 每一步的确认人是谁，确认是否留痕。

推演开始时创建 `实施与验收.md`（状态 In Progress），推演结果作为首条记录。发现问题先补流程或文档定义，再进入实现。推演暴露的流程漏洞可触发本规范自身的修订（第 8 节）。

### 步骤 5：小切片实现
每次只完成一个可验证切片，例如"字段读写与校验"或"删除确认"。实施记录只写：目标、改动范围、测试结果、未解决问题。无需日报。每个切片完成后一个独立 commit（可验证单元即提交单元）。

### 步骤 6：验收与收尾
在 `实施与验收.md` 记录：通过的测试、迁移/回滚证据、已知遗留和用户验收。然后：Agent 从代码反推校准受影响基线（独立 commit，Echo 抽查确认）→ 创建 `归档说明.md` → 把 `升级总览.md` 状态改为 Completed → 整目录移入 `archive/upgrades/` → 更新 `00_项目导航.md`。

**导航更新规则**：`00_项目导航.md` 只在三个点更新——升级启动（步骤 0，登记当前升级）、范围冻结（步骤 3，标 Frozen）、验收收尾（步骤 6，更新版本与归档链接）。导航只反映项目级事实，升级内部过程不更新。

**不动数据的升级只走步骤 0 + 步骤 5**，可跳过步骤 4（模拟推演），记录可以合并写在一个文件里。

## 7. Agent 协作规则

1. 同一轮可以收集多份建议，但只指定一位"综合者"更新 `综合与决策.md`。
2. Agent 开始建议前先读取 `00_项目导航.md`、当前升级的 `升级总览.md` 和已冻结的决定。
3. Agent 输出必须标注它是事实核对、方案建议、风险清单还是实施结果。
4. Agent 不得将自己的建议写成 Current/Frozen，除非维护者明确授权并完成综合。
5. 发现重复文档时，不新建第三份总结；在综合文档中标注主来源和替代关系。
6. 任何冲突先回到实际数据、当前源码和 Current 文档核实，再讨论方案。

## 8. 元规范自身的演进（本规范适用）

本规范是"元规范"（管流程的流程），**它自身的修改不走升级五件套**，否则就是给规范建升级档案，纯属套娃。

演进方式：**原地修订 + git 提交 + 变更记录追加一行 + 顶部版本号递增**（V1.1 → V1.2 …）。涉及原则性变化（如核心约定、流程骨架）时，需用户确认后再把状态标为 Current。
