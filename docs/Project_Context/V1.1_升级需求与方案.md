# Hermes Recall V1.1 升级需求与方案

> 状态：Historical（V1.1 已于 2026-08-12 完成；本方案已被综合，权威见 [综合与决策](/docs/archive/upgrades/V1.1/综合与决策.md)；文件名为历史命名，V1.1 后不再新建含版本号命名）  
> 产品目标版本：V1.1  
> 依据：既有路线图、数据模型、PRD 与测试计划

## 1. 升级目标

V1.1 同时完成两项有限升级：

1. 让单条 Recall 能表达“这是什么记忆、涉及什么、重要程度、与哪些记录有关”。
2. 让用户可使用具有“回响”辨识度的自然语言完成高频操作，同时保持现有直白表达、数据准确性和危险操作安全。

V1.1 的定位是稳定数据 Contract 与交互 Contract，不是完成关联图谱、主动回顾或通知生态。

## 2. 范围

### 2.1 必须纳入（P1）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| V11-REQ-01 | 结构化记忆字段 | 支持 `memory_type`、`importance`、`entities`、`related_ids` 的创建、读取、更新、搜索/展示与校验。 |
| V11-REQ-02 | 旧数据兼容 | 现有 V1.0 Record 可读取；Migration 有预检、备份、执行后校验和失败恢复。 |
| V11-REQ-03 | 原文与历史保护 | `content` 不因 AI 或回响式文案被改写；每项写入保持 History 语义。 |
| V11-REQ-04 | 回响式自然语言交互 | 覆盖新增、查看、搜索、完成、归档、删除确认和 Reminder 入口；直白表达继续可用。 |
| V11-REQ-05 | 歧义与安全门 | 低置信度、多目标、删除和批量变更在确认前零写入。 |
| V11-REQ-06 | Reminder 语义边界 | 个人未来提醒与系统轮询/看门狗明确区分；不因系统自动化描述误建个人 Reminder。 |
| V11-REQ-07 | 质量与版本治理 | Validator 覆盖完整 Contract；时间使用带时区 ISO 8601；统一产品、Skill、Schema 与内部版本展示。 |
| V11-REQ-08 | Gateway 缺陷修复 | 修复 BUG-V11-001：一次 Provider 重试耗尽只向 Feishu 显示一条最终错误提示。 |

### 2.2 明确不纳入

- SQLite、Vector Memory 或语义检索；
- 自动发现关系、主题聚合、Weekly Review、自动修改关联记录；
- 多平台通知、Provider/Identity/Routing 正式落地；
- 完整 Simple Mode、Personal Mode、Setup Wizard；
- 回响式交互的开放式诗歌/隐喻解析、独立持久化 Schema 或大规模 Core 重写。

## 3. 推荐的最小数据方案（待评审冻结）

建议将新字段收敛在可选 `memory` 对象中，而不分散增加多个顶层字段。这样保持 V1.0 Record 的现有核心字段稳定，并为将来的 SQLite 映射保留聚合边界。

```json
{
  "id": "recall_...",
  "content": "用户原始输入",
  "category": "工作待办",
  "priority": "normal",
  "memory": {
    "memory_type": "task",
    "importance": "normal",
    "entities": ["项目复盘"],
    "related_ids": []
  }
}
```

### 3.1 字段 Contract 建议

| 字段 | 建议 Contract | 与现有字段的分工 |
|---|---|---|
| `memory.memory_type` | 单值枚举：`task`、`idea`、`fact`、`preference`、`experience`、`unknown`。 | 描述信息性质；`category` 仍用于用户可见的五分类与组织。 |
| `memory.importance` | `low`、`normal`、`high`，默认 `normal`。 | 描述长期记忆价值；`priority` 继续描述当前执行紧急程度。 |
| `memory.entities` | 非空字符串数组，去重、保持用户可读文本；不在 V1.1 引入实体类型或全局实体表。 | 供展示和后续检索准备；不改变原文。 |
| `memory.related_ids` | 有效 Record ID 的去重数组；V1.1 仅表达轻量关联，不包含类型、方向或置信度。 | 建立显式连接；关系图谱能力留给后续版本。 |

### 3.2 兼容与默认值

- V1.0 Record 缺失 `memory` 时应视为合法，不得因读取而写回。
- Migration 创建 `memory` 时，默认值为 `memory_type: "unknown"`、`importance: "normal"`、空数组；不得伪造实体或关联。
- 新建记录可由 Hermes 建议结构化字段；不确定时使用默认/空值并向用户说明，不能把低置信度推断伪装成事实。
- `related_ids` 指向不存在或被删除的记录时，Validator 必须报告；具体清理或保留策略在冻结时确定，不能静默丢失关联。
- 若本方案获批，Schema 需提升为一个新兼容版本；产品版本、Skill 版本和 Schema 版本分别管理。

## 4. 回响式交互方案

### 4.1 最小 Intent Contract

回响式表达与直白表达必须先归一化为同一个 Intent，再调用既有 Core/CLI。不得建立第二套写入逻辑。

```text
Intent = {
  action,              # add | list | search | done | archive | delete_request | reminder
  target_query,
  payload,
  reminder_time,
  confidence,
  requires_confirmation
}
```

### 4.2 支持入口

| 意图 | 回响式例子 | 行为 |
|---|---|---|
| 新增 | “让回响记住：……” | 保存正文，不把引导语写入 `content`。 |
| 查看 | “听听回响” | 只读查询。 |
| 搜索 | “寻找关于 X 的回声” | 关键词搜索。 |
| 完成 | “让 X 落幕” | 唯一目标时完成；多目标时澄清。 |
| 归档 | “把 X 放进旧日回响” | 只归档，不隐式完成或删除。 |
| 删除 | “让这条回响远去：X” | 仅发起确认，明确确认后才删除。 |
| 提醒 | “和回响约定，明天下午三点提醒我……” | 仅在解析到明确个人未来时间时创建/更新 Reminder。 |

### 4.3 交互规则

- 文学化只用于入口与反馈；时间、状态、目标、错误原因、Record ID 与确认提示必须准确、明确、可扫描。
- 查看和搜索不得产生写入或 History。
- “落幕”“归档”“删除”不可互相隐式映射。
- 低置信度、无目标、多目标和批量操作先澄清；删除、批量完成、批量归档必须展示范围并等待确认。
- “每 5 分钟检查 Provider”等系统自动化描述不是个人 Reminder；可记录为想法或进入自动化工作流。

## 5. 实施顺序

1. **范围冻结与基线**：确认第 3 节字段 Contract、AI 建议/用户纠正策略、悬空关联策略、Schema 版本；备份生产数据；建立失败测试。
2. **数据垂直切片**：实现 `memory` 读写、升级、Validator、Markdown View 和搜索/展示；完成旧数据 Migration 的预检、备份、恢复与对账。
3. **交互垂直切片**：先新增/查看，再搜索/目标解析、完成/归档、删除确认、Reminder 边界；每步均复用同一 Core 行为。
4. **治理与缺陷**：统一版本显示；补充 History Contract；修复并回归 BUG-V11-001。
5. **回归与验收**：运行 V1.0 回归、V11-NLU、Migration 与隔离的 Feishu/Gateway 测试；仅在用户明确同意时进行真实平台验收。

## 6. 测试与完成门禁

### 6.1 自动化与隔离测试

- 建立 `V11-NLU-001` 至 `V11-NLU-030`：意图映射、直白兼容、原文保护、歧义/删除/批量安全、Reminder 与系统轮询边界。
- 所有写入测试使用临时数据目录，并比较执行前后的 JSON 与 History。
- 覆盖新/旧 Schema、非法枚举、重复 ID、无效关联、带时区时间、Migration 失败恢复与 View 重建。
- 覆盖既有 CRUD、Reminder、Scheduler、History、Markdown View 与 Feishu 现有链路回归。
- 以 `V11-GW-001` 验证 Provider 重试耗尽时仅产生一条最终 Feishu 错误提示。

### 6.2 完成条件

V1.1 仅在以下条件全部满足后完成：

- 数据与 Intent Contract 已冻结并记录；
- 新字段可创建、读取、更新、搜索、展示和校验；
- 旧数据迁移可预检、备份、验证并从失败恢复；
- 原始 `content`、现有 CLI 和 V1.0 主流程无回归；
- 回响式与直白表达对同一动作产生相同 Core 结果；
- 危险或歧义操作在确认前零写入；
- 个人 Reminder 不与系统轮询混淆；
- 版本口径一致，BUG-V11-001 回归通过；
- 文档、CLI 帮助、Skill 规范与测试结果同步；
- 用户完成阶段验收。

## 7. 需要先确认的决策

1. 是否采纳 `memory` 子对象与第 3 节枚举/默认值？
2. AI 对 `memory_type`、`importance`、`entities`、`related_ids` 的建议是否需要用户逐项确认，或仅在低置信度时澄清？
3. `related_ids` 的悬空引用在删除目标后是阻止删除、自动移除，还是保留并显式标记？
4. V1.1 是否包含 BUG-V11-001（其归属为 Gateway 集成层，非 Recall Core）作为同一发布验收项？
5. 哪些字段需要进入默认 Markdown View 与关键词 search，哪些仅在详情页展示？

在以上决策确认前，本方案保持 Proposed；不应开始 Schema 或 Core 改造。
