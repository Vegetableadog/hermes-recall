## 2. 项目定义

Hermes Recall（回响）是面向 Hermes Agent 的本地智能备忘录与个人长期记忆模块。

它不只是传统 Todo 工具。项目的长期方向是连接用户过去保存的信息、当前上下文和未来提醒，使 Hermes 能在合适的时间重新唤起相关信息。

核心理念：

> Recall = Hermes 对用户过去想法、计划和信息的回响。

当前产品基线 v1.0 的重点是先建立可靠、可长期使用的记录与提醒闭环，而不是提前实现完整的语义记忆系统。

## 3. 项目目标

### 3.1 当前目标

当前阶段需要稳定支持以下闭环：

1. 用户用自然语言表达需要记录的内容；
2. Hermes 负责语义理解、分类、标签和提醒时间判断；
3. Recall 将结构化记录持久化到本地 JSON；
4. 用户可以查询、更新、完成、归档或删除记录；
5. 对具有明确时间的记录，由统一 Scheduler 检查并触发通知；
6. 系统保留操作历史，并可生成便于阅读的 Markdown 视图。

### 3.2 长期目标

长期目标是将 Recall 从智能备忘录逐步发展为 Hermes 的 Personal AI Memory System，使其具备：

- 结构化记忆理解；
- 记录之间的关联；
- 周期性回顾与主题总结；
- 基于上下文的主动召回；
- 可扩展的多平台通知；
- 面向普通用户和高级用户的不同使用模式；
- 面向长期数据量的数据库与语义检索能力。

这些长期目标目前属于 Target 或 Idea，不代表已经实现。

## 4. 核心原则

### 4.1 JSON 是当前唯一事实来源

`recall.json` 是当前记录数据的 Single Source of Truth。

Markdown 文件由 JSON 单向生成，只承担阅读和展示职责，不与 JSON 双向维护，也不应作为主数据手工编辑。

### 4.2 保留用户原始表达

记录的 `content` 用于保留用户原始表达。AI 生成的分类、标签或其他结构化信息不能静默覆盖原始内容。

### 4.3 明确时间才主动提醒

只有内容包含可确定的提醒时间时，才创建定时提醒。没有明确时间的信息只记录，不主动打扰用户。

### 4.4 记录、调度与通知分离

Recall 负责保存“需要记录什么”和“何时需要提醒”。Scheduler 负责检查到期事件，通知层负责将消息发送到目标平台。

当前实现已经完成基础职责分离；更完整的 Provider、Identity 和 Routing 抽象仍属于后续规划。

### 4.5 兼容与数据安全优先

后续升级必须优先保证：

- 既有 JSON 数据可读取或可迁移；
- 用户原始内容不丢失；
- Markdown View 可继续生成；
- 已有 Reminder 流程不被意外破坏；
- 当前 Feishu 通知能力保持可用，或提供明确迁移方案。

## 5. 版本体系

Hermes Recall 分别管理产品版本、Skill 发布版本和数据 Schema 版本。三者描述的对象不同，不要求每次同时变化。

| 版本类型 | 当前值 | 表示含义 | 典型变更原因 |
|---|---:|---|---|
| 产品基线版本 | v1.0 | 用户可感知的功能阶段 | 新增一组产品能力或完成一个路线阶段 |
| Skill 发布版本 | 1.0.3 | GitHub、SkillHub 等渠道上的可安装包版本 | 功能、修复、文档、安装或发布配置变化 |
| 数据 Schema 版本 | 1.01 | `recall.json` 顶层及记录结构版本 | 字段、约束或迁移逻辑发生变化 |

日常面向用户介绍时，默认使用产品版本，例如“Hermes Recall v1.0”。Skill 发布版本主要用于安装、发布和排障；Schema 版本主要用于数据兼容、升级和恢复。

### 5.1 当前版本来源

- 产品基线 `v1.0`：对应当前已经形成的智能备忘录与提醒闭环；
- Skill 发布版本 `1.0.3`：来自 `SKILL.md` 的发布元数据；
- Schema 版本 `1.01`：来自核心脚本中的 Schema 常量及当前 JSON 顶层版本。

下一阶段产品版本计划为 v1.1。是否同步调整 Skill 和 Schema 版本，应由该阶段的实际发布内容与数据模型变化决定。

## 8. 当前限制与已知问题

### 8.1 源码内部 `v2` 标识不一致

`recall.py` 的模块说明和 CLI 帮助目前使用内部标识 `v2`，与产品基线版本 `v1.0` 不一致。

该标识不代表产品版本，也不改变 Skill 发布版本或数据 Schema 版本。计划在产品 v1.1 开发阶段统一源码、CLI、README 和项目文档中的版本显示口径。

### 8.2 Reminder 模型尚未达到目标状态机

当前源码使用简化的提醒状态：

```text
pending / sent / failed / cancelled
```

原始设计规划的目标状态机包含 `triggered`、`sending`、`delivered` 和 `retry` 等更细状态。当前还没有实现完整的投递生命周期、自动重试次数和错误上下文。

### 8.3 Gateway 模式存在投递确认窗口

当前 Gateway 模式下，Recall 在输出提醒文本后将记录置为 `sent`，随后由 cron 负责实际平台投递。如果脚本输出成功但平台投递失败，Recall 记录与 cron 投递状态之间可能短暂不一致。

该问题不影响当前基础提醒流程的使用，但在升级可靠 Reminder 状态机时需要优先解决。

### 8.4 当前搜索不是语义搜索

当前搜索以内容和标签的关键词匹配为主，尚未实现向量检索或基于上下文的语义召回。

### 8.5 当前通知能力以 Feishu 为主

代码中虽然已有通知职责分离的基础，但 Provider Interface、统一身份映射和多平台路由尚未正式实现。

## 9. 源码与运行组件

仓库中的主要组成如下：

```text
hermes-recall/
├── SKILL.md
├── README.md
├── LICENSE
├── scripts/
│   ├── recall.py
│   ├── recall_scheduler.py
│   └── validate_recall.py
├── references/
│   ├── feishu-gateway.md
│   └── publishing.md
└── docs/
    └── 01-project-overview.md
```

各部分职责：

- `SKILL.md`：Hermes Agent 使用 Recall 时遵循的操作规范；
- `README.md`：安装、配置和快速使用入口；
- `scripts/recall.py`：当前 Recall Core 与 CLI；
- `scripts/recall_scheduler.py`：可分发的统一提醒调度包装；
- `scripts/validate_recall.py`：数据完整性检查；
- `references/`：专项配置、排障和发布资料；
- `docs/`：产品、架构、数据、路线和测试的正式项目文档。

本机运行时可以存在使用绝对路径的部署脚本，但部署件不应代替仓库中的通用实现。

## 11. 文档状态约定

项目文档使用以下状态区分信息成熟度：

- **Current**：与当前源码和运行基线一致的事实；
- **Target**：已经确定方向、但尚未完全实现的目标设计；
- **Idea**：仍需验证或讨论的远期设想；
- **Historical**：历史设计输入，不再作为当前规范。

发生冲突时按以下顺序核实：

1. 当前数据与实际运行结果；
2. 当前源码和可执行测试；
3. 标记为 Current 的正式项目文档；
4. 标记为 Target 的设计文档；
5. Idea 或 Historical 文档。

任何 Target 在实现、测试和验收完成前，都不能自动升级为 Current。
