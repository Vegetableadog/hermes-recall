# FR-003 回响演化引擎（Memory Evolution）需求整理

> 来源：FR-003_Memory_Evolution_回响演化引擎需求文档.docx（原始载体，保留在输入材料/ 目录）
> 日期：2026-08-11
> 回答的问题：一条回响如何表达随时间的发展变化？
> 是否已被综合：否（待步骤 2 综合）

## 核心理念

一条回响不是静态记录，它是一段持续发展的事件。Recall 应该能够回答：

- "这件事情之前发生了什么？"
- "现在进行到哪里？"
- "下一步应该做什么？"

最终目标：让 Hermes Recall 从"记录事情"升级为"理解事情如何发生、变化和结束的长期个人记忆系统"。

## 4.1 Timeline 时间线

为每条重要 Recall 增加事件轨迹（示例）：

```json
{
  "id": "recall_xxx",
  "content": "确认车辆上牌进度",
  "timeline": [
    { "date": "2026-08-10", "event": "创建回响" },
    { "date": "2026-08-11", "event": "已联系少轩", "result": "后天三点上牌" }
  ]
}
```

## 4.2 状态模型升级（五状态）

```text
pending → in_progress → waiting → completed → archived
```

- pending：尚未开始
- in_progress：正在处理
- waiting：等待外部反馈（可记录等待对象）
- completed：事情闭环（可记录完成时间与完成说明）
- archived：历史保存

## 4.3 父子回响关系

当一个事项产生新的目标时：不覆盖，建立关联（parent_id）。

```text
父回响：确认上牌进度
  ↓
子回响：跟进上牌完成结果
```

## 5. 数据结构建议

```json
{
  "id": "recall_xxx",
  "content": "",
  "status": "waiting",
  "parent_id": "",
  "timeline": [{ "date": "", "event": "", "result": "" }],
  "latest_update": { "time": "", "summary": "" },
  "schema_version": "1.3"
}
```

注：FR-003 建议的 schema_version 为其目标版本标注；V1.1 的 Schema 版本独立管理，具体版本号在综合阶段确定（产品/Skill/Schema 三版本独立）。

## 6. 用户交互设计（场景）

- 场景 1（进展更新）："已经联系少轩，他说明天下午三点上牌" → 不覆盖原记录；增加 Timeline、更新状态、判断是否生成新回响
- 场景 2（完成）："资料已经收到" → 标记 completed；保存完成时间与完成说明
- 场景 3（等待）："还在等邹总回复" → 更新 waiting；记录等待对象（邹总）

## 7. 与 Reminder Lifecycle 的关系

- Reminder Lifecycle 解决：提醒之后怎么办
- Memory Evolution 解决：事情变化怎么办
- 完整生命周期：记录回响 → 提醒回响 → 回应回响 → 演化回响 → 封存回响

## 8. 开发约束

1. 不破坏已有 JSON 数据
2. 支持 schema_version
3. 保留历史信息
4. 不允许无意义复制记录
5. 优先保证长期数据可迁移
6. 先设计再修改，不要直接进行大规模重构

## 9. 测试方案（Test 01-05）

- Test 01：创建新回响 → 基础字段正常
- Test 02：更新进展 → Timeline 增加记录
- Test 03：产生新目标 → 创建子回响并关联
- Test 04：完成事项 → 历史保留
- Test 05：查询历史 → 可以看到完整演化过程
